## How an order is placed

1. zod checks the form: name 2 to 80 characters, phone optional (up to 20
   characters of digits, spaces and `+ / - ( )`), `publicCode` a UUID,
   quantities whole numbers (blank is 0).
2. `placeOrder`: a filled honeypot is refused. An order with the same
   `publicCode` already exists: done, the customer lands on its confirmation.
   Then one query loads the open round's products with remaining stock, and
   the rows are checked: known products, no duplicates, at least one
   quantity, each at most min(remaining, 20).
3. One `db.batch()`: the order row is inserted only while a round is open
   (the round is selected in the insert, not taken from the form); each line
   only while its stock covers the quantity, joined to the order's round.
   Name, unit and price come from the server's copy of the offer.
4. A used `publicCode` fails the whole batch: treated as a repeated submit.
   An order row not written: orders are closed. A line not written: the order
   is deleted (lines cascade) and the form shows which quantities are too
   high, using fresh stock.

Queries per order: code lookup, offer, one batch (order plus one statement
per line), and a delete only when stock ran out.

## Decisions

- **Field names** are English (`name`, `phone`, `website`), like the rest of
  the code; the labels are Slovenian. Plan section 7 updated.
- **Rows post pairs** of `roundProductId` and `quantity`. A sold-out row shows
  "Razprodano" and posts nothing.
- **Errors**: name and phone next to their fields; quantity problems in a
  notice above the products and in the marked row ("Naročite lahko največ
  3." or "Medtem je razprodano."), computed from the stock at re-render. The
  form keeps everything typed and the same `publicCode`. A malformed
  `publicCode` gets a new one.
- **Without JavaScript**: the number fields and the submit button work; the
  total appears on the confirmation page. The browser also blocks a quantity
  above the field's `max` before sending (its own message, in the browser's
  language); the server checks again.
- **With JavaScript**: minus and plus buttons (rendered `hidden`, shown by the
  script), live total, the native number spinners hidden. The script is
  about 55 lines in the page.
- **Confirmation page** shows the round, the customer's name (not the
  phone), the lines, the total, payment and the round's delivery info. A
  cancelled order shows "To naročilo je preklicano." Unknown or malformed
  codes answer 404.
- **Honeypot** is a `hidden` field named `website`. A filled one returns
  "Naročila ni bilo mogoče oddati. Osvežite stran in poskusite znova."

## Known limits

- If the same form is sent twice at the same moment and the first send then
  fails on stock, the second lands on a confirmation page that answers 404.
  Needs a double click while the last items sell out.
- If Kristjan changes a price between page load and submit, the order uses
  the new price (the server's, as the plan requires); the live total on the
  page showed the old one.

## After review

- An unknown or malformed code on `/narocilo/hvala/[code]` still answers 404,
  but with its own page: the order was not found, if it was just submitted it
  was not saved, and a button back to `/narocilo`. The order details moved to
  `src/components/OrderConfirmationDetails.astro`. Checked in `astro dev`
  and with `wrangler dev` on the built worker. `astro preview` shows the
  generic 404 page for every 404 instead; that is its Vite preview server,
  not the Worker.
- Price changes during an open round stay as they are; the README says not
  to change prices while a round is open.
- The phone hint is confirmed.
