## Decisions

- `@cloudflare/vitest-pool-workers` is deprecated; replaced by
  `@cloudflare/vitest-plugin` 1.9.0 with vitest 5.1.1 (asked and approved).
- `vitest.config.ts` declares the test bindings itself (`DB`, `SESSION`,
  compatibility date and flags) instead of reading `wrangler.jsonc`: the plugin
  tries to load `main`, which is the Astro entrypoint package, and fails.
  The two files must be kept in step (comment in the config).
- `wrangler.jsonc` has no `database_id` and no KV `id`. Local development works
  without them. For deploy, Wrangler can create both and write the ids back;
  the exact steps go in the README in M7.
- Prettier formats `.jsonc` with trailing commas; Wrangler accepts them.
- `--color-border-strong: #8a7a66` (3.7:1 on bg) added for form controls.

## Image serving CPU

Method: a 500 KB random BLOB in the local `Image` table, served by a test route
from the production build (`astro preview`, workerd). CPU is the `utime + stime`
of the workerd processes over 150 to 200 requests per route, divided by the
number of requests. Locally D1 runs inside the same workerd process, so these
numbers include D1's own work: they are an upper bound for the Worker alone.
In-Worker timings come from `performance.now()` (1 ms resolution locally).

| Route                                                 | 150 KB  | 250 KB  | 500 KB        |
| ----------------------------------------------------- | ------- | ------- | ------------- |
| Small row, no BLOB (baseline)                         | 3.9 ms  | 3.9 ms  | 3.9 ms        |
| `SELECT data` (BLOB as array), `new Uint8Array(data)` | 10.9 ms | 15.2 ms | 26.5 ms       |
| `SELECT hex(data)`, `Uint8Array.fromHex()`            | 4.9 ms  | 5.2 ms  | 6.2 to 7.2 ms |

Inside the Worker, decoding the array-shaped result (1.78 MB of JSON for 500 KB)
takes 5 to 6 ms at 500 KB, about 3 ms at 250 KB and 2 ms at 150 KB, plus up to
1 ms for `new Uint8Array()`. With `hex(data)` both steps stay under 1 ms.

Conclusion: serving a 500 KB image the planned way costs above 5 ms of Worker
CPU. Kristjan chose option a (hex read).

### Hex read, Worker share (second measurement)

The first table mixes the Worker with local D1 and the local HTTP plumbing. To
separate them, each part was measured on its own with `wrangler dev` on the
production build, 300 requests per route, plus microbenchmarks inside the
Worker isolate (each step repeated 20 to 100 times, so the 1 ms timer
resolution does not matter).

| Route (500 KB image)                                 | Process CPU per request | Difference = cost of the step                 |
| ---------------------------------------------------- | ----------------------- | --------------------------------------------- |
| Bare Worker returning "ok" (local plumbing only)     | 2.7 to 2.9 ms           | floor, not Worker CPU in production           |
| Astro route returning "ok", no D1                    | 3.7 ms                  | +0.9 ms Astro routing (Worker)                |
| Astro route, one small D1 row                        | 4.7 to 4.9 ms           | +1.1 ms D1 round trip (Worker and D1)         |
| `SELECT length(hex(data))`                           | 6.0 ms                  | +1.2 ms reading and hexing the BLOB (D1 only) |
| `SELECT hex(data)`, no decode                        | 6.9 ms                  | +0.9 ms 1 MB string out of D1 and parsed      |
| `SELECT hex(data)`, `fromHex()`, 500 KB response     | 7.9 ms                  | +1.0 ms decode and 500 KB response            |
| For comparison: `SELECT data` (array)                | 28.2 ms                 |                                               |
| For comparison: Workers KV `get(..., "arrayBuffer")` | 5.4 to 5.6 ms           |                                               |

Inside the Worker isolate (microbenchmarks, 500 KB): parsing the hex result
0.08 to 0.10 ms, `Uint8Array.fromHex()` 0.13 to 0.19 ms, building the response
body 0.15 to 0.18 ms. The array read for comparison: parsing 5.3 to 5.4 ms plus
0.2 ms for `new Uint8Array()`.

Result for the hex read of a 500 KB image:

- Upper bound for the Worker: 7.9 ms minus the plumbing floor (2.8 ms) minus
  D1's own BLOB work (1.2 ms) = **3.9 ms**. This still includes D1's query
  handling and the local HTTP output, so the Worker alone is lower.
- Estimate: Astro routing 0.9 ms + the Worker's part of a D1 call (under
  1.1 ms) + image work about 0.5 ms = **about 2 to 2.5 ms**.
- Both are under 5 ms. Caveat: measured on an Apple Silicon VM; Cloudflare's
  servers may be somewhat slower per core. The real CPU time per request is
  visible in the Cloudflare dashboard after the first deploy (checked in M7).

The V8 CPU profiler was also tried, but locally it attributes time of other
isolates on the same thread to the Worker (its totals exceeded the whole
process), so its numbers are not used.

## By hand (Kristjan)

1. Install Node.js 22.23.4 or newer (Astro 7.4 requires it).
2. In the repo: `npm ci`. The lockfile was created on Linux arm64 and includes
   the macOS binaries, so `npm ci` installs the right ones.
3. `npm run db:migrate:local`, then `npm run dev` and open http://localhost:4321.
4. `npm test`, `npm run check`, `npm run build`, `npx prettier --check .`.
5. Optional: `npx astro telemetry disable` (Astro CLI sends anonymous usage data
   by default; this concerns your machine, not the site).
6. Review and commit.
